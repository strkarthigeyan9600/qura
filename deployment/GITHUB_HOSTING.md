# Deploy the complete app from GitHub

GitHub Pages only hosts static files. Deploy this repository's Docker image on a persistent server to run the frontend, API, SQLite, photo storage, research worker and WebSocket together under one HTTPS origin.

The root render.yaml defines a Render Docker service with a persistent 5 GB disk and a standard paid compute plan. No service has been purchased or created by adding this file. Review Render's current price before deploying. Smaller compute may be insufficient for six-model training and SHAP. Docker/cloud execution has not yet been verified.

1. Sign in to Render, select New > Blueprint, and connect strkarthigeyan9600/qura.
2. Review the standard service and disk charges. Supply a unique QURA_DEMO_PASSWORD (12+ characters, uppercase/lowercase, number and symbol) in the dashboard. JWT secret is generated by Render.
3. Deploy. The startup command uses the host PORT, adds its supplied HTTPS RENDER_EXTERNAL_URL to allowed Origins, and initializes fictional accounts/resources once on the persistent disk. Restart does not reseed consent. No local private database or credentials are included.
4. Open the assigned Render URL. Both frontend and /api are served there, without a separate proxy. Confirm /api/health returns JSON, login/session/logout work, then verify every role and the five-role chain.
5. Research features need trained models. From the service shell, run python -m backend.seed_demo --train --reports once to create the six-model benchmark and fictional reports. This explicit demo command resets fictional research consent; do not use it with real patient records. Training can take substantial time/resources.
6. To retain the existing Vercel frontend, generate vercel.json using tools/configure_vercel.py with the assigned Render origin, commit and redeploy Vercel. Verify cookies and WebSocket/polling behavior through the proxy separately.

This is a prepared deployment, not a live deployment. Requires the owner to connect hosting/GitHub accounts and approve the hosting charges. After deployment, test profile consent, photo review, consultations, admin dispatch, driver acceptance, capacity reservation/rejection, live locations, arrival/handover/admission, reports, PDF downloads, multilingual core UI and authorized research jobs. Verify data survives restart and secrets/uploads are private. Routes/traffic remain simulated and hospital capacity manually reported; deploying does not create real ambulance/hospital integrations.
