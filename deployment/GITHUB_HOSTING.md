# Deploy the complete app from GitHub

GitHub Pages only hosts static files. Deploy this repository's Docker image on a persistent server to run the frontend, API, SQLite, photo storage, research worker and WebSocket together under one HTTPS origin.

The root render.yaml now selects the free compute plan with no paid disk. This is a disposable demonstration: SQLite accounts, uploads, model checkpoints and emergency records are lost on restart/redeploy/spin-down. Free services sleep after 15 idle minutes. Six-model training and SHAP may exceed free compute limits. Full durable hosting is not supplied by this free configuration. Docker/cloud execution has not yet been verified.

1. Sign in to Render, select New > Blueprint, and connect strkarthigeyan9600/qura.
2. Verify that the selected instance is Free and has no persistent disk. The blueprint enables QURA_PUBLIC_DEMO=true. No demo password entry is required; startup generates an internal seed password. Anyone may enter all five fictional demo roles. JWT secret is generated by Render.
3. Deploy. The startup command uses the host PORT, adds its supplied HTTPS RENDER_EXTERNAL_URL to allowed Origins, and initializes fictional accounts/resources once in temporary storage. A restart with cleared storage creates fresh fictional accounts; saved records do not survive. No local private database or credentials are included.
4. Open the assigned Render URL. Both frontend and /api are served there, without a separate proxy. Confirm /api/health returns JSON, login/session/logout work, then verify every role and the five-role chain.
5. Research features need trained models. From the service shell, run python -m backend.seed_demo --train --reports once to create the six-model benchmark and fictional reports. This explicit demo command resets fictional research consent; do not use it with real patient records. Training can take substantial time/resources.
6. To retain the existing Vercel frontend, generate vercel.json using tools/configure_vercel.py with the assigned Render origin, commit and redeploy Vercel. Verify cookies and WebSocket/polling behavior through the proxy separately.

This is a prepared deployment, not a live deployment. Requires the owner to connect hosting/GitHub accounts. No paid service is authorized. After deployment, test profile consent, photo review, consultations, admin dispatch, driver acceptance, capacity reservation/rejection, live locations, arrival/handover/admission, reports, PDF downloads, multilingual core UI and authorized research jobs. Verify data survives restart and secrets/uploads are private. Routes/traffic remain simulated and hospital capacity manually reported; deploying does not create real ambulance/hospital integrations.

For all existing features with durable data at no hosting-service cost, run on your own computer; shared availability then depends on that computer and its network remaining online. A free cloud design with external durable database/object storage requires a storage migration and separate provider accounts; it is not implemented here.

## Public one-click demonstration

With QURA_PUBLIC_DEMO=true, runtime storage is forced to a separate temporary qura-public-demo directory, regardless of QURA_STORAGE_DIR. This protects an existing normal database from accidental reuse. Allowed origins and role permissions still apply. No credentials are requested in the demo UI. Normal deployments with this flag absent remain password-protected. The public demo is shared/disposable, including administrator access; use fictional records only. Disable external AI. New deployments read render.yaml automatically; existing Render services may need QURA_PUBLIC_DEMO=true added in their Environment settings followed by redeploy. The Vercel frontend still requires the actual Render API rewrite; GitHub Pages alone cannot run this backend. No live hosting changes have been made without account access.
